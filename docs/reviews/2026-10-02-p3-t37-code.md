Date: 2026-10-02
Scope: `git diff f5fc0e9..7467b91` on `phase/3-scoring`: the lineup data function, API route, and shared DTOs. First production caller of `computed_cache`; first `apps/web` consumer of `@sideline/core`.
Reviewer: code-reviewer subagent (read-only).

## Verdict

CHANGES REQUIRED at review time (one Major). Fixed before Batch H; see commit `438ffdd`.

## Findings

### [M1] Major — `currentAssignment` could misalign with `resolveSlots`' output on an unknown slot type

`apps/web/lib/server/lineup.ts` built `currentAssignment` straight from `starters_json`, assuming it stays index-parallel with `resolveSlots`' filtered `slots` array. That holds for `BN`/`IR`/`TAXI` (Sleeper's `starters` array has no entry for those at all, matching `resolveSlots`' own exclusion), but not for a slot type Sleeper lets a user start a player in that `resolveSlots` doesn't recognize — exactly the case LINEUP-1's own `UNKNOWN_SLOT_TYPE` warning anticipates. `resolveSlots` drops that slot from `slots`; `starters_json` still carries an entry for it, shifting every later slot's assignment by one. Low probability for any league using only standard/IDP slot types (none observed in the verified league), but silent and data-corrupting (wrong player shown locked/current in the wrong slot) rather than a loud failure, if it ever occurred.

**Fix (commit `438ffdd`):** `buildCurrentAssignment` re-applies the identical two-part filter `resolveSlots` uses (reserve types, then `slotType in SLOT_ELIGIBILITY`) so the two arrays stay in lockstep regardless of unknown slot types. Regression test added reproducing the exact misalignment. Re-verified: `pnpm verify` 930 tests, 0 failures.

### [m1] Minor — `matchupMultiplier`'s own reasons are discarded

`lineup.ts` destructures only `{ multiplier }` from `matchupMultiplier`'s result; its `MATCHUP_AVG_POS_UNAVAILABLE`/`MATCHUP_MULTIPLIER_CLAMPED` reasons never reach a player's DTO `reasons`. Zero practical impact today (`alpha = beta = 0` makes `m` always exactly `1`, so neither reason can fire). Revisit once T3.5c's real backtest ships a non-zero `alpha`/`beta` — surface these reasons in the player DTO at that point. Not fixed; backlog.

### [m2] Minor — no lock/fallback signal when a team has zero `schedule` rows for the target week

If `schedule` has no row at all for a team/week (not just a missing precise kickoff, but a full coverage gap), `kickoffUtc` falls through to `null` and `isLocked` treats that as "not locked" (its own documented defensive default). Pre-existing data-availability edge case, not introduced by this task; T3.7 is just the first caller to surface it to a user. Not fixed; informational.

### [m3] Minor — untested edge cases (verified safe by inspection)

A roster player id absent from the `players` table, and a roster with zero eligible players after removing reserve/taxi, are both handled defensively (`p === undefined` fallbacks; every read helper guards `ids.length === 0`; `solveOptimalAssignment` handles `numPlayers === 0`) but untested at the `getLineup` level. Not fixed; backlog.

### [n1] Nit — `applyAvailability` called twice with identical inputs

Once inside `recommendLineup` (to build its internal adjusted value) and once in the DTO-building loop (to get the displayed `value`). Pure function, so both calls provably return the same number — no double-discount, just redundant computation and a duplication smell. Not fixed; a future refactor could have `recommendLineup` return each player's resolved adjusted value directly.
