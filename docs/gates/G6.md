## Summary

Phase 6 hardened Sideline for self-hosted release: an optional `APP_PASSWORD` login gate (HOST-8, signed HTTP-only session cookie, 30-day expiry, constant-time comparison, 5/min/IP rate limit), security headers and structured logging on every response, a Docker/Unraid self-hosting story (PUID/PGID defaults fixed to match the real entrypoint, a new Unraid Community Applications template, a full `docs/self-hosting.md` rewrite), a PWA manifest and icon set, and consolidated preseason/offseason states and League-page polish (desktop tables, "You" markers) across the UI. It ran in four batches (ADR-017): A and B built the features (one Major fixed: an unbounded-memory rate-limiter map; two Blockers fixed: a real axe color-contrast violation, a stale-test-caused red a11y suite); C ran the three gate-prep tasks (T6.4 full regression/fresh-install/upgrade/auth-e2e/60-minute soak, T6.5 whole-repo security review, T6.6 final UX review of every screen), all of which came back clean; D (the planned T6.7 fix round) was skipped because Batch C returned zero Blocker/Major findings to fix (logged as an ADR-017 amendment in `docs/DECISIONS.md`).

A real security bug was found and fixed during Batch A: `clientIp` trusted the spoofable FIRST `X-Forwarded-For` entry instead of the last (proxy-appended) one. T6.5's whole-repo security review independently re-traced the fix and confirmed it holds, along with the full auth lifecycle, the constant-time comparisons, and the rate limiter's bounded memory. `pnpm audit` has 7 advisories (4 high, 2 moderate, 1 low), every one traced to `@lhci/cli` or `drizzle-kit` (devDependencies only) and empirically confirmed absent from both the worker's `pnpm deploy --prod` output and the web's `.next/standalone` bundle -- zero runtime exposure.

## Batch E: post-gate fix round (Steph's live testing)

This gate was first presented on 2026-10-04 with automated checks PASS. Steph answered two of the three open questions immediately (single shared password is fine; yes to a container registry, GHCR specifically) and flagged a real bug from testing on her phone: the Lineup page recommended "3 swaps available, projected +0.0 pts" with a swap chain that netted to zero real benefit. Five tasks fixed this and one approved follow-up landed, all reviewed and verified before this report was finalized (full writeup: `docs/DECISIONS.md`'s ADR-017 "Amendment (2026-10-04, post-gate, Steph's live testing)"):

- **T6.8** (`89edcde`, analytics-engineer): root cause was WR/FLEX slot-eligibility overlap plus the Hungarian solver's tiebreak having no preference for the player's current slot, so tied-value permutations could report a meaningless swap chain. Fixed with an optional current-assignment stability bonus in `solveOptimalAssignment`, strictly ordered against the existing tiebreak epsilon so it never changes which *value* is optimal.
- **T6.9** (`dd94a74`, frontend-engineer): added the same `pointDelta >= 0.05` materiality floor the Home page already used, to the Lineup page's summary banner and swap list, as defense against any genuinely-tiny-but-nonzero delta.
- **T6.10** (`96a495b`, qa-engineer): a property test generalizing the fix -- swap any two unlocked, mutually-eligible, filled slots in an optimal lineup and feed that back in as "current"; must report zero swaps. Deliberately avoided a tautological construction the original brief suggested (documented in the test itself).
- **T6.11** (`666e787`, devops-engineer): wired GHCR into CI (Steph's approved choice), scoped `packages: write` to the `docker` job only, push gated on `github.event_name == "push"` so PR/fork builds never log in or push. Dormant until a real GitHub remote exists.
- **T6.12** (`31b3f72`, frontend-engineer): a code review Major -- the `0.05` floor was duplicated as an inline literal in two places -- fixed by hoisting it into one shared `apps/web/lib/client/lineup-recommendation.ts` module both pages import.

A code review (`docs/reviews/` -- see commit `a0f0b9f` era; APPROVE after the one Major above was fixed) and a targeted UX review of the Lineup page (APPROVE, zero findings, independently confirmed live on real fixture data that the default view now correctly shows "Your lineup is already optimal") both passed clean.

**Two re-runs of the full `pnpm gate --amd64` suite were needed to reach a genuinely clean state**, surfacing three more real, pre-existing issues along the way (all fixed, all unrelated to the Lineup bug itself):
- `e2e/lineup.spec.ts`'s `LINEUP-FLOW-5` failed consistently (all 3 Playwright projects) -- stale against the T6.8/T6.9 fix's correct new behavior, not a regression. Fixed by qa-engineer, pinning the test to a week/mode combination hand-verified to produce a material swap.
- `vitest.config.ts`'s coverage-exclusion glob (`**/*.perf.test.ts`) never matched the literal filename `apps/web/lib/server/perf.test.ts` (no prefix before `.perf`), a latent gap dating to Phase 4 (T4.7) -- so this wall-clock perf-budget test was getting V8 coverage instrumentation on every `pnpm gate`/`pnpm test:coverage` run despite the adjacent code comment's explicit intent to exclude it. Fixed directly (one-character glob correction, `vitest.config.ts`).
- T6.10's new property test (heavier per-iteration than its sibling) hit vitest's 5000ms default timeout under coverage instrumentation even though it finishes in well under 1s uninstrumented. Given an explicit 30s timeout, matching this config's existing convention for other CPU-heavy test categories.

Final `pnpm gate --amd64` run (commit `471c7a6`, `dirty: true` only from the gate script's own output files mid-write): **11/11 PASS**, route JS for `/` and `/l/[leagueId]/lineup` unchanged from the original G6 run (153,439 B and 179,129 B respectively), Docker images unchanged in size, Lighthouse and axe counts unchanged.
